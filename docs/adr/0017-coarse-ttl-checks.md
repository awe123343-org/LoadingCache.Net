# ADR-0017: Opt-in coarse TTL hit checks

Accepted, 1 October 2026.

Precise timestamp sampling is a material part of fixed-expiration hit cost. Provide `.EnableCoarseExpirationChecks()` on the existing builder, disabled by default, to let applications accept delayed TTL detection in exchange for a cached timestamp read. This is an explicit freshness-contract change, not a timer precision guarantee. Do not expose a general-purpose coarse `TimeProvider` or a resolution setting.

Only the existing lock-free fixed-TTL value path without TTI uses coarse time. It still acquires and validates the value/write publication, duration bound and non-retired entry identity. Coarse time may predate a recent precise write; a negative age is fresh, and the usual publication recheck still prevents mixing value generations. Near-deadline/conflict/task fallbacks retain precise checks. Automatic-refresh, variable-expiry, weak-reference and owned-value configurations keep their existing precise paths. Runtime duration changes retain the same precise mutation and scheduling protocols; hit detection remains subject to this opt-in delay.

Every public Build path rejects combining the option with any provider other than `TimeProvider.System`, including configurations that do not have an eligible TTL fast path. The engine's precise provider is unchanged. Writes, explicit refresh completion, automatic refresh eligibility/backoff, load timeout, policy-age/quiet views, expiration scheduling and cleanup never use the cached timestamp. Physical retirement always prevents a late coarse hit from reviving an entry. A precise quiet miss need not remove an expired entry; a subsequent coarse value lookup may still hit until exact cleanup or the ticker catches up.

TTI and TTL+TTI deliberately remain outside this option. Using a frozen timestamp to touch access time, or to decide whether an exact touch is necessary, could cause early expiry and violate ADR-0016's one-millisecond bound. A future coarse-TTI proposal would need a separate contract and evidence.

One lazy, process-wide internal ticker samples `Stopwatch.GetTimestamp()` and publishes a monotonic non-decreasing timestamp with a volatile write. Hits use a volatile read. It requests `Thread.Sleep(1)` between samples. Returned timestamps never exceed the corresponding precise time, so TTL detection can be late but is not made early by the coarse clock. Sleep and scheduling have no upper wake-up bound: GC, thread starvation and system suspension can freeze the value for arbitrary periods. Platform-dependent typical lag must be reported as an observation, not a maximum or service guarantee.

The ticker is a background thread, starts only for an enabled eligible cache, suppresses the creating request's execution context, and runs for the process lifetime. It owns no cache, entries or caller context; disposal of one cache cannot stop another cache's clock. A reference-counted or idle-parked lifecycle would add wake-up and ownership races for one shared thread; keep this version simple. There is no thread or timer started for default configurations.

This change does not modify ADR-0007 counters, ADR-0013 reliable-write bounds or ADR-0014 read transport/scheduling. Lossy policy observations remain independent of expiry; only the separately requested TTL read-check contract is relaxed.

`CoarseExpirationTests` uses a per-engine threadless clock seam to freeze and advance coarse time without sleeps. It covers default-off and opt-in behaviour, custom-provider rejection across builder personalities/orderings, exact cleanup/quiet/task/scheduler paths, TTI bounds, precise write/refresh timestamps, timeout, and shared-clock progress/monotonicity after a cache is disposed. The test seam cannot mutate the process-wide ticker. The [performance report](../benchmarks/coarse-ttl-20261001/README.md) uses alternating independent processes on .NET 8 and .NET 10, with MemoryCache controls and explicit power/runtime records, and includes observed ticker lag.
