# ADR-0016: Bounded fixed-TTI access coalescing

Accepted, 1 October 2026.

Fixed expire-after-access (TTI) hits previously advanced the access timestamp by a forward-only CAS on every successful read. Repeated readers of one entry contend on that cache line even when their access times are almost identical. We accept bounded access-time approximation on the existing lock-free fixed-expiration path to reduce these writes. This changes the public expiration and policy-age contract; the old freshness guard band did not already permit approximation.

For the duration bound acquired by a read, define `tolerance = min(accessBound >> 20, floor(TimestampFrequency / 1000))` in raw timestamp units. A validated fixed-TTI hit whose sampled age is at most this tolerance skips the access CAS. Larger positive ages use the existing `TouchPublished` protocol. The threshold rounds down, is at most duration / 2^20, and cannot exceed one millisecond. Providers with less than one raw tick per millisecond have a zero coalescing threshold.

With a stable duration, the recorded timestamp can lag the most recent successful access by at most the tolerance. Consequently, TTI expiration can occur that much early, `AgeOf` can overstate age by that much, and `GetExpiresAfter` can understate remaining duration by that much. Repeated skips do not accumulate error because they compare against the recorded access, not against a previous skipped read. This does not permit serving values past their recorded deadline or changing TTL. The raw freshness guard band continues to select the exact locked fallback near a deadline.

Runtime `SetDuration` and its fixed-policy alias `SetExpiresAfter` preserve recorded age. Access information already coalesced under an older duration is not recoverable. After a shrink, its error can exceed the new tolerance and can cause an immediate miss; the absolute error remains at most one millisecond until a real touch or value replacement. This bounded behavior is accepted rather than adding per-entry state or rewriting age during a duration change.

The scope is only the validated lock-free fixed-TTI hit. Publication pairing, `Updating`, retirement, refresh/rollback fencing, and the forward-only CAS retry rule remain unchanged. A CAS retry can make access recording more precise. Locked touches remain exact: task views, near-deadline and publication-conflict fallbacks, 32-bit TTI reads, weak references, owned values and automatic-refresh configurations do not coalesce. Variable expiry continues to use its existing callback protocol. The cap is cached per engine from its stable clock frequency; no entry field or configuration option is introduced.

Alternatives were recording every access (the existing contention cost), an uncapped duration-relative threshold (large errors for long TTI), and a fixed one-microsecond threshold (unrelated to configured duration and not the selected POC). The one-millisecond cap gives a duration-independent maximum while short durations retain a proportionally smaller tolerance. Exact per-access semantics remain available through configurations already using the locked path; this decision does not add an opt-out switch.

`FixedAccessTouchTests` covers the inclusive tolerance boundary, actual advancement beyond it, the maximum early-expiry interval, long-duration capping, both duration-change method names, task views and other exact configurations. Its assertions retain exact behavior on 32-bit processes. `FixedWritePublicationTests` covers publication/rollback fencing and the `Updating` fallback. Existing sub-tick, backward-clock, timestamp-wrap, TTL and expiry tests remain unchanged. Formal performance validation compares the same baseline and patch processes on both runtimes, including ten-reader cycle/hot TTI and TTL controls, with a separate one-day TTI single-reader case. Performance results are evidence for the tradeoff, not a guarantee for every workload.

Measurements and all process medians are recorded in the [benchmark report](../benchmarks/tti-touch-20261001/README.md).
